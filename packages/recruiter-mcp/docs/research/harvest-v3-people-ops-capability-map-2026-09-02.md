## 0. Constraints that shape every metric below

Four facts about the API and this tenant decide how a People Ops recipe has to be built, so they come first.

The application row carries no hire timestamp. `GET /v3/applications` returns `status` (`in_process`, `rejected`, `hired`, `converted`), `rejected_at`, `created_at`, `last_activity_at`, `stage_id`, `stage_name`, `source_id`, `referrer_id`, `recruiter_id`, `coordinator_id`, `job_post_id`, `prospect`, and custom fields, and nothing named `hired_at` (`D/reference/0015-get_v3-applications.md:607-624`; a grep of the whole 175-page mirror for `hired_at` returns nothing). The `hired` status is set "once an offer is closed and the hire endpoint has fired" (`:841`), so it depends on someone calling `POST /v3/applications/{id}/hire` (`D/reference/0018-post_v3-applications-id-hire.md:7`) rather than on the offer being accepted. The hire date therefore lives on the offer (`resolved_at` with `status=Accepted`, `D/reference/0130-get_v3-offers.md:7,611`) or on the opening (`closed_at` with `application_id` populated, `D/reference/0139-get_v3-openings.md:727`), and the three counts — accepted offers, `status=hired` applications, openings closed by hire — are three different numbers on this tenant. The cleanup census names "accepted offer still `in_process`" as one of the contradictions reserved for manual review (`M/greenhouse-cleanup-census-and-disposition.md:38-40`).

Offers are versioned rows, not one record per candidate. Changing `starts_on`, `opening_id`, or a custom field flagged `trigger_new_version` creates a new row with `version+1` and marks the prior row `Deprecated`; `current_only=true` collapses the chain to the latest version per application (`D/reference/0130-get_v3-offers.md:7,578,766`). The TI census confirmed the shape live: offers are separate records per re-extension, and `sent_on` was populated on 53 of 62 accepted offers (`M/ti-time-in-process-pull.md:45`). Any rate whose denominator is "offers" must say whether it counts chains or rows.

Hires are mostly private candidates on this tenant. 1,955 of 2,156 hires (90.7 percent) carry `private: true`, and a Job Admin without the "Can create and view private candidates" permission does not see them in Greenhouse either, so a scoped recruiter's read returns 201 of 2,156 hires by design (`M/private-equals-hired-stop-gate.md:17-23`). Site admins are not exempt; the permission is user-specific (`M/greenhouse-site-admin-private-inference-refuted.md:11-13`). A People Ops pack that runs under a line recruiter's scope will report hire counts roughly one-tenth of reality without any error surfacing. The pack has to run as an operator principal that holds that permission, or it has to disclose the private-candidate exclusion count on every hire-denominated number.

The reads are expensive at tenant scale. Harvest v3 pages by `id` descending, 100 rows by default and 500 maximum, cursor-only after the first request (`D/guides/0003-pagination.md:73-79`), under a fixed 30-second rate window whose documented example limit is 75 requests (`D/guides/0000-api-rate-limiting.md:22,34`). The tenant holds 1,128 jobs, 4,184 openings, and 700,389 applications — 1,401 pages at 500 per page (`M/greenhouse-cleanup-census-and-disposition.md:16-18`). The server's read-all engine reads at 500 per page (`S/read-all.ts:15`) under a per-tool deadline and a hard page ceiling (`:185`), so a People Ops recipe that scans applications will time out; it has to filter server-side on the offer, opening, or job endpoints and only then bridge to applications by id. One further API-level fact: the list-endpoint guide states that GET endpoints "are only accessible by site admin users" (`D/guides/0002-list-endpoints.md:48`); the server reads under an org-wide service credential and enforces recruiter scope itself (`S/private-custom-fields.ts:4-6`), which is why the private-candidate and private-custom-field gates are the server's job rather than Greenhouse's.

## B. Definitions the API supports, and which ones the exec reports already use

### Hire date and the hire denominator

Three counts exist and they disagree. The one every published artifact uses is the accepted offer: `offers.status = Accepted`, dated by `resolved_at`. The weekly req report counts `signed` and `declined` by `resolved_at` falling inside the Friday-anchored week and `offerExtended` by `created_at` (`T/lib/recruiting-ops/delivery-source/req-week-report.ts:178-196`). The staging hydration loader pulls offers two ways for the same reason — every version since quarter start by `created_at`, and current versions by `resolved_at` since the reporting week, so a decline or acceptance of an offer created before the quarter is not missed (`T/lib/recruiting-ops/delivery-source/staging-hydration-source-loader.ts:205-217`). The All Hires sheet's `acceptedDate` is `resolved_at` and it throws if an accepted offer lacks one (`T/lib/recruiting-ops/delivery/all-hires-renderer.ts:54,72-73`); the employee referral report windows on `resolved_at[gte]`/`[lt]` and refuses an offer with no `resolved_at` (`T/lib/recruiting-ops/employee-referral-report.ts:350-351,1052-1057`); the ELT hires block is "every org-wide accepted offer that week" and the legacy doc's write-time bucketing was logged as a diff class against `resolved_at` as canonical (`M/elt-and-exec-report-formats.md:17,29`). The People Ops pack should adopt the same definition and report the other two counts — `applications.status = hired` and openings closed with `application_id` set — as reconciliation lines, not alternatives.

### Time to hire

The API supports three defensible clocks, and each answers a different question.

The candidate clock runs from `applications.created_at` to `offers.resolved_at` on the accepted offer. It is the only one computable without stage history, and it is honest for inbound applicants, because for them the application timestamp is first contact. For outbound-sourced candidates the application is created when a screen is booked, so this clock measures data entry (`M/ti-time-in-process-pull.md:25`).

The process clock runs from the recruiter-screen stage's `application_stages.entered_at` to `resolved_at`. This is the clock the TI time-in-process memo used, keyed on exact stage names (`Recruiter Phone Screen` for the screen, `Manager / Tech Screen` for the hiring-manager round), and it produced the published medians: US screen-to-start 53.3 days and India 46.7 days for 2026 accepts, with the post-interview window decomposed as last-interview-to-offer-entered 4.1/2.9 days and entered-to-signed 4.3/1.2 days (`M/ti-time-in-process-pull.md:45`). The last-interview anchor was `max(interviews.starts_at)` on dated rows.

The job clock runs from `jobs.opened_at` (or the seat's `openings.opened_at`) to `resolved_at`; that is time to fill, below.

No published report computes a time-to-hire figure on a schedule. The exec workbook's only elapsed-time facts are `daysOpen` and `lastAdvanceDays` (`T/lib/recruiting-ops/exec-definitions.ts:298-308`), and the offer sheet's `resolutionDays` is created-to-resolved in whole UTC days (`T/lib/recruiting-ops/delivery/final-offer-sheet-renderer.ts:220-228`). A People Ops pack that emits time to hire is publishing a new number, and it should carry the TI memo's process-clock definition so the two agree.

### Time to fill

Time to fill has two clocks. The job clock, `jobs.opened_at` to the accepted offer's `resolved_at`, understates reopened or cloned requisitions because `opened_at` records only the first open (`D/reference/0124-get_v3-jobs.md:520`) and a clone starts its own clock (`:501`). The seat clock, `openings.opened_at` to `openings.closed_at` on openings whose `close_reason_id` resolves to a `Hire -` reason, is the definition the capacity program's vocabulary calls a "filled recorded opening" (`T/docs/recruiting-ops/RECRUITING_CAPACITY_SOURCE_OF_TRUTH.md:208`), and it is the one to publish, with the 882-of-4,102 missing-close-reason share disclosed as coverage. `openings.application_id` gives the join to the hire without going through offers at all (`D/reference/0139-get_v3-openings.md:727`).

### Offer to start

Offer to start has one clock, `resolved_at` to `starts_on` on the current version (`current_only=true`), with the chain read separately to measure start-date slippage (each `starts_on` edit is a new version). The TI memo published this as accept-to-start, 14.4 days US and 12.3 days India for 2026, and the All Hires sheet writes `starts_on` as `start_date` (`T/lib/recruiting-ops/delivery/all-hires-renderer.ts:75`; the server aliases the same field, `S/harvest-v3-registry.ts:659-661`). Greenhouse never learns the actual start; that is an HRIS fact (§C).

## C. What Harvest v3 cannot reach

Retention, first-year attrition, and regretted loss need the employee record after day one, which Greenhouse never holds. The join keys the API offers are `users.employee_id` (the HRIS id, but only for Greenhouse users, `D/reference/0169-get_v3-users.md:580`), `candidates.linked_user_ids` (`D/reference/0057-get_v3-candidates.md:509`), `openings.opening_id` and `departments.external_id`/`offices.external_id` as partner-supplied HRIS identifiers (`D/reference/0139:7`; `D/reference/0085:7`), and, in practice, the candidate's email address. HiBob is the live HRIS and its departments do not match Greenhouse's (`T/docs/recruiting-ops/RECRUITING_CAPACITY_SOURCE_OF_TRUTH.md:147-159`), so the join is candidate-email to HiBob employee, which is PII the projection deliberately drops off every endpoint except the candidate's own row (`S/tools/evidence-projection.ts:259-285,494-504`). Retention therefore has to be computed in the analytics platform against an HRIS extract, never inside the MCP.

Onboarding completion, actual start date, and no-shows are likewise HRIS facts. `starts_on` is proposed; nothing in the API records that the person showed up.

Compensation bands exist in Greenhouse only as pay-transparency ranges on job posts (`pay_input_ranges`) or as a job-level `currency_range` custom field, both org-configured and, on this tenant, unverified. If Finance owns bands in a separate system, band-vs-offer needs that feed.

EEOC per person is reachable in the API and must not be reached by this tool: the page states that the endpoint returns row-level responses where the product's own report returns aggregates (`D/reference/0089-get_v3-eeoc.md:7`), which is the external constraint the ambition-by-default posture requires for a narrowing. Aggregate-only, minimum-cell-size output computed server-side is the sound design; it needs the `harvest:eeoc:list` scope on the service credential, which no record here confirms.

Reopen history, assignment history, and department history are not in the contract at all (§A rows 9, 16, 18). The capacity program already names the dated allocation history and the job-to-segment crosswalk as things it must build outside Greenhouse (`T/…/RECRUITING_CAPACITY_SOURCE_OF_TRUTH.md:47-50,251-254`); the People Ops pack inherits those gaps rather than solving them.

Requisition approval as a business event ("approved headcount") is not the Greenhouse `open_job` approval flow; CAP-011 and CAP-012 keep them separate (`:241-242`).

## E. Recipe sketches for the top five

Each sketch follows the structure the six existing recipes share: scoped reads through `readAllScopedRows`, a fact layer built by a `facts.ts` builder, metrics registered in `METRIC_REGISTRY` with `requiredFields` so a projection omission can block the answer (`S/tools/evidence-projection.ts:294-308`), a `summary.field_limitations` block, and a `buildAnalysisCompleteness` envelope with named exclusion reasons and the provenance detector (`S/tools/source-quality.ts:168-192,254-265`; `S/resolution/analysis-result.ts:49-71`).

### E1. `analyze_offer_outcomes` (rows 1, 2, 21)

Reads: `list_offers` with `job_ids` from the resolved scope, `resolved_at[gte]`/`[lte]` for the window, no `status` filter, `current_only=false` (the chain is needed for the per-row denominator); a second `list_offers` with `current_only=true` for the per-application denominator; `list_rejection_details?application_ids=` for the `Rejected` offers' applications; `list_rejection_reasons?include_defaults=true`.

Joins: offer → application (`application_id`) → rejection detail → reason `type.key`; offer → job for the department/office dimension.

Metrics: acceptance rate per application = accepted current offers ÷ (accepted + rejected current offers); acceptance rate per extension = accepted rows ÷ (accepted + rejected rows), `Deprecated` and `Created` excluded from both; decline reasons = `Rejected` current offers grouped by `type.key` then `name`, with an `unclassified` bucket for offers whose application is not rejected; decision days = `resolved_at − sent_on` in calendar days, median and 25th–75th, over rows with both dates.

Disclosures: the two denominators and their difference (the re-extension count); the count of `Rejected` offers with no rejection detail (the unclassifiable declines); rows missing `sent_on` (excluded from decision days, not from rates); private-candidate exclusion count when the actor is not an operator; the noon-UTC backfill artefact if more than a threshold share of `resolved_at` values sit at exactly 12:00Z.

Completeness: `inventoryComplete` only when both offer reads and the detail read finished; `dataFreshnessOk` false when `sent_on` coverage falls below the census baseline (53 of 62); `provenance` from the offer `created_at` distribution.

### E2. `analyze_time_to_hire_and_fill` (rows 3, 4, 5)

Reads: `list_offers?status=Accepted&current_only=true&job_ids=…&resolved_at[gte]…`; `list_applications?ids=` for the accepted set (for `created_at`, `source_id`); `list_application_stages?application_ids=` in batches of 50 (`S/tools/stage-latency.ts:17,345-359`); `list_job_interview_stages?job_ids=<one id>` per job; `list_openings?application_ids=` for the seat clock; `list_close_reasons`.

Joins: offer → application → stage rows → the job's stage definitions, resolving the recruiter-screen stage by exact name per job (default `Recruiter Phone Screen`, overridable by a name list); offer → opening via `openings.application_id`.

Metrics: candidate clock = `resolved_at − applications.created_at`; process clock = `resolved_at − entered_at(screen stage)`; job clock = `resolved_at − jobs.opened_at`; seat clock = `openings.closed_at − openings.opened_at` on openings whose close reason starts with `Hire -`; offer-to-start = `starts_on − resolved_at`. All in calendar days, median and 25th–75th, split by office group and by source category.

Disclosures: hires whose application never entered the screen stage (`entered_at` null), reported as a count and excluded from the process clock; outbound-sourced hires (source `type.name` ∈ {Prospecting, Agencies}) flagged as artefact-prone on the candidate clock; openings without a close reason; jobs with `copied_from_id` set, whose job clock is a lower bound; the stage-name list used.

Completeness: partial whenever any per-job stage read failed (that job's hires drop from the process clock only); `dataFreshnessOk` false if screen-stage `entered_at` coverage is below a floor.

### E3. `analyze_hires_by_period` (rows 6, 8, 13)

Reads: `list_offers?status=Accepted&current_only=true&resolved_at[gte]…` (or `starts_on[gte]=today` in upcoming-starts mode); `list_applications?ids=`; `list_jobs?ids=`; `list_departments`, `list_offices`, `list_sources`, `list_referrers`; `list_candidates?ids=` only when the caller asks for names, and only on the operator profile.

Joins: offer → job → department (walk `parent_id` to a top-level group) and office (first `office_ids` entry as primary, with the multi-office count disclosed); offer → application → source `type.name` and referrer `user_id`.

Metrics: hires per calendar month (by `resolved_at`) by department, office, and source category; referral share = hires with a referrer or a `Referral`-category source ÷ hires; upcoming starts = accepted current offers with `starts_on` on or after today, listed by week with department and office.

Disclosures: the ELT definition in force (accepted offer by `resolved_at`, not by write time); jobs spanning more than one office; the reconciliation lines — `applications.status=hired` count and openings-closed-by-hire count for the same window — so the three counts are visible together; private-candidate exclusions.

Completeness: standard read status; `partial` when any department or office id fails to resolve.

### E4. `analyze_headcount_fill` (rows 4, 7, 16, 17)

Reads: `list_jobs?status=open` and `?status=closed&closed_at[gte]=…` for the window; `list_openings?job_ids=` for those jobs (all states); `list_close_reasons`.

Joins: opening → job for department/office and to drop openings on `draft` or `is_template` jobs.

Metrics: the demand reconciliation the capacity program specifies — beginning open recruitable openings, plus openings opened in the window, minus openings closed with a `Hire -` reason, minus openings closed with any other reason, equals ending open (`T/…/RECRUITING_CAPACITY_SOURCE_OF_TRUTH.md:89-95`); fill rate = hire-closed ÷ all closed in the window; job age distribution over open jobs from `opened_at`; median seat age for open openings from `openings.opened_at`.

Disclosures: openings on draft jobs (excluded, counted); closed openings with no close reason (counted as "closed, outcome unknown", never as filled — `M/greenhouse-cleanup-census-and-disposition.md:30-32`); `Not Filling` closures listed separately; the statement that Greenhouse openings are not approved headcount (CAP-011).

Completeness: `inventoryComplete` requires both job reads and the opening read to finish; provenance on `openings.opened_at`.

### E5. `analyze_hiring_team_load` (rows 9, 11)

Reads: `list_job_owners?job_ids=` (all types), `list_job_hiring_managers?job_ids=`, `list_users?deactivated=false`, `list_openings?job_ids=&open=true`, `list_applications?job_ids=&status=active` (for per-recruiter active pipeline via `recruiter_id`), `list_interviews?job_ids=&starts_at[gte]…&status=scheduled,awaiting_feedback,complete` (one call per status, since the filter is single-valued), `list_interviewers?interview_ids=`, `list_scorecards?interviewer_ids=&interviewed_at[gte]…`.

Joins: owner/user → jobs and open openings; interviewer `user_id` → users; interviewer → scorecard by `scorecard_id` for submission.

Metrics: per recruiter (`job_owners.type=recruiter`, `responsible` flagged) — open reqs, open openings, active applications, hires in window; per hiring manager — open reqs and active applications; per interviewer — dated interviews attended in window, distinct applications, scorecards submitted ÷ scorecards owed, median `submitted_at − interviewed_at` hours; a team-capacity line — distinct interviewers and total seats per week.

Disclosures: assignment is point-in-time (no history); users who are `job_owners` (TA staff) removed from the interviewer panel with the count shown; scaffolding interview statuses excluded and their count named; deactivated users appearing on historical rows; `job_title` empty tenant-wide so no title-based classification was attempted; agency users (`agency_id` set) separated.

Completeness: `partial` if the interviewers join was truncated for any batch; provenance over `interviews.starts_at`.

## The thing you're not seeing

The pack's biggest risk is that the same offer read produces four different "hires" figures depending on principal and parameters, and no endpoint gap comes close to it. A scoped recruiter sees roughly one hire in ten because of the private flag; the planner's offer path counts `Deprecated` versions in its total; the ELT and referral pipelines count current accepted offers by `resolved_at`; the opening close reason says something else again. None of those is wrong on its own terms, and none of the current tools prints the reconciliation. The first thing E3 should emit, before any dimension, is the four counts for the same window on one line, and every other recipe should inherit that line.

The second thing is the stale description on `search_my_offers`, which tells the model compensation is withheld while the projector passes it (`S/tools/evidence.ts:95` versus `S/tools/evidence-projection.ts:692`). A model that believes the description will not ask for comp; a model that reads the row will see it. The description should be corrected in the same change that ships E1, and whether the tenant's base-pay definition is `private` should be measured with `search_my_custom_fields?field_type=offer` before anyone promises a comp-versus-band metric.
